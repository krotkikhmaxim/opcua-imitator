# Единое серверное состояние сигналов — схема и контракты (ТЗ #5)

Итог реализации ТЗ «Единое серверное состояние сигналов» (`docs/ТЗ.md`):
что построено, как потоки данных ходят на самом деле, какие контракты
у команд, подтверждений, владения, снимков и изоляции таймлайна.
Пошаговые разделы с командами и живыми проверками — в
[`README.md`](../README.md); этот документ — карта целого (§18 ТЗ).

## 1. Схема фактических потоков данных

```
            ┌─────────────────── браузер (SPA, build-free) ───────────────────┐
            │ App.tsx: REST-снимок + WS-дельты (seq, ревизии) →               │
            │ рендерится ТОЛЬКО подтверждённое; команды с op_id + ревизиями   │
            └───────────────┬────────────────────────────┬────────────────────┘
                   REST /api/…                       WS /ws
┌───────────────────────────┐            ┌───────────────────────────┐
│ API: /api/signals/write,  │            │ ValuesFeed (тик 0.5 c):   │
│ /write_batch, /reset,     │            │ signals_snapshot при      │
│ /api/states/load          │            │ подключении; дельты       │
└─────────────┬─────────────┘            │ {v,r,s}+seq; owners при   │
              │                          │ смене версии владения     │
              ▼                          └─────────────┬─────────────┘
┌─────────────────────────────────────────────────────┐  │
│ OPCSignalBus.apply_changes — ЕДИНСТВЕННАЯ дверь     │  │ read_value
│ записи во встроенный сервер и кэш:                  │◄─┘
│  1) проверка ВЕСЬ пакет (существует / тип / право / │
│     владение / ожидаемая ревизия) → отказ ЦЕЛИКОМ;  │
│  2) применение по одному в порядке передачи;        │
│  3) подтверждение: SignalCache.confirm → карточка.  │
└──────┬─────────────────┬──────────────────────┬─────┘
       ▼                 ▼                      ▼
EmbeddedOpcUaServer  SignalCache          наблюдатели записи:
opc.tcp://…:4840,    карточки {value,     WriteLedger (сверка со
узлы read-only       revision, source,    станцией, 200k),
для внешних          changed_at}          DiagnosticsJournal (1k),
(Режим B)                                 SnapshotStore (atomic file)
       ▲
       │ write_value_at(SourceTimestamp шкалы сценария), source=scenario:<run_id>
┌──────┴──────────────────────────┐   ┌──────────────────────────────────┐
│ ScenarioEngine: N прогонов,     │   │ PlaybackService (таймлайн):      │
│ владение, пауза/продолжение;    │   │ ЗАМОРОЖЕН — PLAYBACK_WRITES_     │
│ сценарии живут в процессе,      │   │ ENABLED=false: play/seek → 409,  │
│ после рестарта не возобновляются│   │ в сигналы не пишет               │
└─────────────────────────────────┘   └──────────────────────────────────┘
```

Правила потока: запись в сигналы идёт только через `apply_changes`;
чтение фидом — через `read_value` (значение-зеркало без роста ревизии);
сценарий пишет через ту же шину с SourceTimestamp своей шкалы и подписью
владельца; плейбэк трендов записи не делает (код сохранён для разморозки
отдельным решением).

## 3. Единый реестр сигналов

Источник тегов — `docs/opcua_input_bindings.json`
(`telemetry.opcua.input-bindings.v1`, 101 вход): `id`, `name`, `type`,
`writable` (может ли имитатор сам писать — у всех входов true),
`opcua_writable` (внешняя запись; НЕ открывает её, см. §6), `project_tag`,
`opcua_node`, `channel/cabinet/module/direction/bit/device/word_address`.
`load_signal_config` читает файл, незнакомая форма → встроенные дефолты;
каждый результат проходит `validate_configs`: дубли id/NodeId, неизвестный
тип, негодное начальное значение — полный список проблем и отказ старта
(невалидная конфигурация не стартует «как получится»). Типы —
`Boolean`/`Int32`/`Double` (наследуемые bool/int/float); приведение —
только таблицей типов, замены нулём нет, NaN/inf отклоняются.
Отпечаток реестра для снимка — `sha256[:12]` по отсортированным
`(id, type, адрес)`.

## 4. Контракты команд и подтверждений

`OPCSignalBus.apply_changes(changes, *, source, op_id=None,
expected_revisions=None, require_writable=False, contract="api",
when=None, owner=None)` → ответ команды:

```json
{"op_id": "…", "status": "applied|partial|rejected|failed|conflict",
 "results": {"<id>": {"status": "applied", "value": …, "revision": 7}},
 "applied": ["<id>"], "errors": []}
```

- порядок определён: проверка всего пакета до первой записи; ошибка
  проверки отклоняет пакет ЦЕЛИКОМ (прошедшие проверка помечаются
  `not_applied/package_rejected`); частичное выполнение возможно только
  от отказа самой записи (`partial`, без отката);
- подтверждение — только после успешной записи: карточка состояния
  `{value, revision, source, changed_at}`; ревизия растёт только от
  применений, чтение её не трогает; источник — имя писца
  (`manual`, `manual_batch`, `reset`, `state_load`, `scenario:<run_id>`);
- дедупликация: повтор с тем же `op_id` и телом в окне 4096 возвращает
  сохранённый ответ с `replayed: true` (записи нет); тот же `op_id` с
  другим телом — `conflict/op_id_conflict` (409);
- `expected_revisions` — оптимистичная блокировка: устаревшая ревизия
  отклоняет пакет целиком (`revision_conflict`, 409).

HTTP-двери: `POST /api/signals/write` `{id, value, op_id?,
expected_revision?}`; `POST /api/signals/write_batch` `{values, op_id?,
expected_revisions?}`; `POST /api/signals/reset` `{signal_ids?, op_id?}`
(значения из реестра: `default`, иначе значение типа; без списка — весь
записываемый набор). Коды → HTTP: 404 unknown_signal, 403 not_writable,
409 owned/revision_conflict/op_id_conflict, 400 invalid_value,
502 write_failed.

WS-контракт (§12): подключение `/ws` начинается с `signals_snapshot`
(тот же построитель карточек, что REST, + текущий `seq` фида); затем
каждый тик (0,5 с) — `signals_update` с монотонным `seq` и изменениями
`{v, r, s}` (пустой тик тоже событие — пропуск отличим от тишины);
`owners` уходит только при росте версии реестра владения. Клиент: дельта
старше известной ревизии не применяется (событие не откатывает
подтверждённое), скачок `seq` → перезапрос снимка, обрыв → баннер
«значения устарели» и блокировка управления до восстановления.

## 5. Владение и разрешение конфликтов

`OwnershipRegistry`: `acquire(owner, signals)` — всё-или-ничего, при
конфликте полный перечень `{signal_id, owner}`; `release(owner_id)`
возвращает освобождённое; `version` растёт только при реальной смене
(на нём держится WS-карта владельцев). Занятый сигнал меняет только его
владелец: сценарий подписывает каждую запись `owner="scenario:<run_id>"`;
ручная запись, пакет, сброс и загрузка состояния в занятый сигнал
отклоняются пакетом с кодом `owned` (409, титул владельца в тексте).
Пауза владение СОХРАНЯЕТ; ошибка держит владение до явного решения
оператора (stop); завершение, остановка и отмена освобождают сразу.
Несколько прогонов работают одновременно, если их объявленные наборы
не пересекаются; пересекающийся старт отклоняется целиком, идущие прогоны
не трогаются. Наборы записанных режимов могут совпадать между собой —
на текущем каталоге второй сценарий всегда 409 (данные каталога —
наблюдение, не инвариант; решение о каталоге за владельцем).

## 6. Внешние OPC UA-записи — Режим B (действующий)

Все публикуемые узлы закрыты для внешней записи (`set_writable(False)`
при старте встроенного сервера; флаг `opcua_writable` из реестра запись
не открывает — legacy-дыра закрыта шагом 2). Внешние клиенты читают и
подписываются; запись возвращает `BadUserAccessDenied`. Управление
значениями — только серверные команды приложения. Режим A (внешние
записи через общий учёт с источником `external_opcua`) НЕ реализован —
переход к нему отдельное решение владельца.

## 7. Сохранение и восстановление

Один атомарный файл `data/server_state.json` (tmp + rename):
`schema="opcua-imitator.server-snapshot.v1"`, отпечаток реестра,
карточки `{v, r, s, t}`, `created_at`, `complete`. Позиция таймлайна и
тренд не сохраняются. Сохранение: после успешных команд, на переходах
сценария (пауза/остановка/завершение/ошибка), периодически во время
прогона (`PERSIST_INTERVAL_S`, 5 с по умолчанию, 0 — выкл), при штатном
останове. Снимок всегда соответствует завершённой границе применения —
высокочастотные шаги сценария файл не пишут. Восстановление при старте
проверяется ЦЕЛИКОМ (схема, отпечаток, отметка, JSON); чужое или битое
отбрасывается весь — начальные значения и явная диагностика, частичной
миграции нет. Годной снимок переносит значения/ревизии/источники как
есть (ревизии не растут) и выставляет значения во встроенный сервер.
После рестарта: сценарии не возобновляются, владение пусто; источник
последнего значения в карточке — не владелец управления.

## 8. Изоляция таймлайна

`PLAYBACK_WRITES_ENABLED=false` (дефолт): play/seek плейбэка трендов
отклоняются (409 «Таймлайн отключён от управления сервером»), load/unload
и статус сохранены — код и данные ждут отдельного решения владельца.
Применение сценария или режима останавливает идущий плейбэк само (хук),
а не отбивает запуск конфликтом. Корректность тренд-файла для работы
остального приложения не требуется: отсутствие файла, битая ячейка или
несоответствие колонок не мешают командам, сценариям, снимкам и WS.

## 9. Диагностика и запуск тестов

`GET /api/diagnostics/events?limit=100` — хвост ограниченного журнала
(1000 записей): операции применения (op_id, источник, сигналы, статус,
ошибки, длительность, ревизии) и события сценариев (старт, отказ старта
с конфликтами, пауза, продолжение, остановка, завершение с агрегатами,
ошибка с эпизодом, освобождение владения). Высокочастотные записи
сценария агрегируются счётчиками прогона. Рост ограничен повсюду:
журнал диагностики 1000, журнал сверок 200 000, окно дедупликации 4096,
неактивные прогоны — 50.

cd backend

## 10. Проверка независимым OPC UA-клиентом

Живые проверки (asyncua-клиент против стенда :4840, не внутреннее
состояние): ручная запись видна чтением узла сразу после подтверждения;
внешняя запись отклонена `BadUserAccessDenied` при живом чтении и
подписках (шаги 2, 7); занятый сценарием сигнал — 409 с титулом
владельца, свободный — 200, после остановки ручное управление вернулось
(шаг 5); восстановленный после рестарта снимка читается с узла сразу
после старта (шаг 8); две WS-клиентские сессии получили одинаковые дельты
(шаги 7, 9).
