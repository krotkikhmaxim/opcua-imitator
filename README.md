# OPC UA Imitator

Система сохранения и загрузки состояния OPC UA сигналов в формате JSON для веб-приложения мониторинга и управления подъёмной машиной (ПМ).

Полное техническое задание: [`docs/ТЗ.md`](docs/ТЗ.md). Итоговая схема
фактических потоков данных и контракты реализации: [`docs/server_state.md`](docs/server_state.md).

## Возможности

- 💾 Сохранение текущих значений всех сигналов в JSON-файл
- ▶ Загрузка сохранённого состояния обратно в OPC UA сервер
- 📥/📤 Импорт и экспорт JSON-конфигураций
- 🗑 Управление сохранёнными состояниями (список, удаление)
- 🔄 Автообновление списка состояний (каждые 10 с)
- ⚡ WebSocket-уведомления о загрузке состояния
- 🧪 Встроенный OPC UA **сервер** (по умолчанию) — публикует сигналы как переменные на `opc.tcp://0.0.0.0:4840`
- 🧪 Режим **имитатора** — только кэш, без сетевого сервера

## Отключённые фичи

- **Имитация аварий** (лист Э3, мнемосхема с аварийными кнопками, плейбек
  тренда, журнал достоверности, эхо станции) — экран убран из навигации
  2026-10-19; его место занял пульт машины (раздел «Пульт машины»).
  Компоненты и API, которыми он пользовался, оставлены в дереве
  (`frontend/src/components/mnemo`, `schematic`, `playback`, `station`) и
  возвращаются одной правкой навигации в `App.tsx`, без восстановления кода.

## Запуск

### Backend

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# режим со встроенным OPC UA сервером (по умолчанию) — слушает opc.tcp://0.0.0.0:4840
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

# режим имитатора (только кэш, без сетевого OPC UA сервера)
OPC_UA_MODE=imitator .venv/bin/uvicorn app.main:app --port 8000

# подключение к реальному OPC UA серверу
OPC_UA_MODE=real OPC_UA_ENDPOINT=opc.tcp://<host>:<port> .venv/bin/uvicorn app.main:app --port 8000
```

Сигналы из `docs/opcua_input_bindings.json` (схема
`telemetry.opcua.input-bindings.v1`) публикуются как переменные во встроенном
сервере: dotted-идентификатор разворачивается в иерархию папок, а NodeId
переменной равен полному IEC-пути (`ns=2;s=Chanel1.Application.GVL.GlobalInOutSignal.x10A3DigitalInput.SQ1_SinhLeftTop`),
как у реального ПЛК. Значения, записанные через веб-интерфейс (имитация),
видны внешним OPC UA клиентам; сами переменные для внешних клиентов read-only.

состояние в `/opt/asutp/state/imitator/*`). Публичных портов контур не

(`CORS_ORIGINS=https://opcuaimitator.ru`,

Ручная приёмка — оверрайд `deploy/compose.debug.yml`: порты только на
`127.0.0.1` сервера, дальше ssh-туннель. Смоук OPC UA —
`scripts/smoke_opcua.py`: обходит дерево адресного пространства, читает
значения и проверяет отказ внешней записи (`BadUserAccessDenied`).

### Единый механизм применения (ТЗ #5, шаг 4)

Все внутренние изменения значений идут через `OPCSignalBus.apply_changes`:
пакет проверяется целиком до первой записи (сигнал существует, право на
запись, тип по единой таблице `signal_types`, ожидаемая ревизия) — ошибка
проверки отклоняет пакет, значения не меняются; затем сигналы применяются
по одному в порядке передачи с результатом по каждому (частичное выполнение
возможно только от отказа записи, отката нет). Подтверждённое состояние
сигнала — `{value, revision, source, changed_at}`; `/api/signals` отдаёт его
рядом со значением. Повтор команды с тем же `op_id` (окно 4096 команд)
возвращает сохранённый результат (`"replayed": true`) и не применяется
дважды; тот же `op_id` с другим телом — конфликт `409`. Статусы команды:
`applied` / `partial` / `rejected` / `failed`. Ручные записи идут с
`source: "manual"`, загрузка состояния — `state_load`; heartbeat по-прежнему
обновляет только SourceTimestamp.

### Владение сигналами (ТЗ #5, шаг 5)

Сценарий до запуска объявляет набор изменяемых сигналов (синтез — весь
реестр, записанный режим — свои сигналы) и получает на него исключительное
владение. Пересекающийся запуск отклоняется целиком (`409`, код
`signals_busy`, в ответе перечень занятых сигналов и их владельцев);
непересекающиеся прогоны живут одновременно. Записи прогона подписаны
`source: owner: "scenario:<run_id>"`, `/api/signals` показывает владельца в
карточке (`owner` — титул, `owner_id`). Ручная запись, пакет и загрузка
состояния в занятый сигнал отклоняются (`409`, код `owned`); свободные
сигналы пишутся. Команды жизненного цикла — серверные (`POST
/api/scenarios/pause`, `/resume`, `/stop`, у последних двух необязательный
`run_id`; без него при нескольких активных прогонах — `409`): пауза замирает
смены и сохраняет владение, продолжение сдвигает базу времени — интервалы
сценария остаются точными. Ошибка ставит прогон с фазой `error` и сохраняет
владение до явной остановки оператором; завершение и остановка владение
освобождают. Heartbeat по-прежнему обновляет только SourceTimestamp (его
перехват — шаг 7).

### Ручное управление и сброс (ТЗ #5, шаг 6)

Каждая правка оператора — серверная команда через общий механизм применения,
никакой оптимистичной подмены значения в UI. Клиент шлёт `op_id` и
`expected_revision(s)` — ревизию на момент чтения; если она ушла (чужая запись
между чтением и применением), пакет отклоняется целиком (код
`revision_conflict`), значение не перезаписывается незаметно, интерфейс
запрашивает актуальное состояние. До подтверждения UI показывает черновик и
состояние «Применение…»; после — все представления получают подтверждённое
значение из `results` команды. Ошибка записи оставляет фактическое значение
сервера и показывает причину. Мнемосхема пишет так же: переключение — команда
с `op_id` и ревизией. Сброс значений идёт через тот же механизм
(`POST /api/signals/reset`): начальные значения берутся из реестра (поле
`default` реестра сигналов), можно сбросить выбранный набор или весь
записываемый; те же правила типов, владения (занятый сценарием сигнал
отклонит сброс кодом `owned`, пакет целиком) и дедупликации `op_id`.
Таймлайн сброс не затрагивает: позиция не меняется, тренд-файл не читается.

### Синхронизация UI и внешние записи (ТЗ #5, шаг 7)

Подключение к `/ws` начинается со снимка всех карточек
(`signals_snapshot` с текущим `seq` фида), затем идут дельты
`signals_update` — каждый тик фида, с монотонным `seq` и карточкой
`{v, r, s}` (значение, ревизия, источник) по каждому изменившему
сигналу. Клиент замечает пропуск в `seq` (потерянные сообщения) и
перезапрашивает снимок; дельта старше известной ревизии не применяется —
событие не откатывает подтверждённое состояние. Карта владельцев уходит
в дельте при смене (`owners`), между снапшотами владение обновляется
опросом раз в 5 с. При потере связи UI показывает баннер «значения
устарели, управление заблокировано» и отключает кнопки применения,
сброса и мнемо-переключатели до восстановления (состояние соединения
также видно бейджем live/опрос в шапке). Несколько открытых клиентов
получают одни и те же подтверждённые дельты; переподключившийся браузер
начинает со свежего снимка и не выдаёт старые локальные значения за
актуальные — записи и так идут командами с `expected_revision(s)`.

**Внешние OPC UA-записи — Режим B (запись запрещена).** Управление
значениями выполняется только серверными командами приложения (API и
UI); все опубликованные узлы закрыты для внешней записи
(`set_writable(False)`, шаг 2 закрыл дыру legacy-полей), чтение и
подписки работают. Независимый клиент видит `BadUserAccessDenied` при
попытке записи; тесты `test_embedded_server.py` закрепляют контракт.
Разрешающая запись конфигурация (`opcua_writable`) не используется;
переход к Режиму A (внешние записи через общий учёт, источник
`external_opcua`) — отдельное решение владельца.

### Снимки и восстановление (ТЗ #5, шаг 8)

Подтверждённое состояние сервера живёт в одном файле
(`data/server_state.json`, путь настраивается): схема
`opcua-imitator.server-snapshot.v1`, отпечаток реестра сигналов,
карточки `{v, r, s, t}` (значение, ревизия, источник, время) по всем
сигналам и отметка завершённости. Запись атомарная (tmp + переименование) —
порванного снимка не бывает. Позиция таймлайна и тренд-данные не
сохраняются.

**Когда сохраняется:** после каждой успешной команды применения (ручная
запись, пакет, сброс, загрузка сохранённого состояния), на переходах
сценария (пауза/остановка/завершение/ошибка), периодически во время
прогона (каждые `PERSIST_INTERVAL_S`, по умолчанию 5 с; `0` отключает) и
при штатном останове сервера. Высочастотные шаги сценария файл не пишут —
снимок всегда соответствует завершённой границе применения, а не
промежуточному состоянию внутри пакета.

**Восстановление при старте:** снимок проверяется целиком — схема,
отпечаток реестра, отметка завершённости, корректный JSON. Повреждённый,
неполный или принадлежащий другому реестру снимок отбрасывается весь:
сервер стартует с начальными значениями и явной диагностикой в журнале
(частичной неявной миграции нет). Годный снимок переносит значения,
ревизии и источники прошлого процесса как есть (восстановление — не
команда применения, ревизии не растут) и выставляет значения в адресное
пространство встроенного OPC UA сервера — внешний клиент видит их сразу
после старта.

**Чего после рестарта нет:** сценарии не возобновляются (прогоны живут в
памяти процесса), владение сигналами пусто. Источник последнего значения
в карточке (`manual`, `scenario:<run_id>`, …) — это кто менял значение
прошлого процесса, а не кто им управляет сейчас.

### Диагностика (ТЗ #5, шаг 9)

`GET /api/diagnostics/events?limit=100` — хвост ограниченного журнала
(1000 записей, старейшие вытесняются): операции применения (op_id,
источник, сигналы, результат, ошибки, длительность, ревизии) и события
жизненного цикла сценариев (старт, отказ старта с перечнем конфликтов
владения, пауза, продолжение, остановка, завершение, ошибка с шагом,
освобождение владения). Высокочастотные записи сценария агрегируются
счётчиками прогона (`writes`/`write_failures`), ошибки и события
управления не агрегируются. Прогоны в памяти сессии вытесняются за
пределом 50 неактивных.

## Конфигурация сигналов

Источник тегов — `docs/opcua_input_bindings.json` (входные сигналы ПЛК и слова
PROFIBUS: `id`, `name`, `project_tag`, `opcua_node`, `type`, `channel`, `cabinet`,
`module`, `direction`, `bit`, `device`, `word_address`). Имитатор публикует их
как `ns=2;s=<project_tag>` и позволяет менять значения через веб-интерфейс для
имитации; внешним OPC UA клиентам переменные доступны только для чтения.
В режиме имитатора значения сигналов хранятся в кэше и обновляются при
сохранении/загрузке состояний. Для реального сервера можно указать `node_id`.

## Сценарии аварий

Имитатор умеет сам «работать» машиной и периодически её ронять: штатные
рейсы клетей, затем эпизод — авария или штатная остановка, затем квитирование
и возврат в работу, и так по кругу. Данные идут с шагом 100 мс, каждое
изменение публикуется с `SourceTimestamp` момента сценария. Цель — дать
станции историю, по которой на вопрос «почему встала машина» есть проверяемый
ответ.

| Сценарий | Что происходит | Видно ли причину после остановки |
|---|---|---|
| `estop_console` | на ходу разомкнут аварийный стоп пульта | да, стоп остаётся нажатым |
| `estop_circuit_glitch` | цепь аварийного стопа разомкнулась на 300 мс | **нет** — только в истории |
| `drive_emergency_off` | нажато аварийное отключение ПЧ | да |
| `inverter_fault` | рост тока до перегрузки, бит аварии и код ошибки инвертора | да, в слове состояния |
| `tp_relay_dropout` | реле ТП отпало без срабатывания защит | да, реле отпавшее |
| `normal_stop` | машинист вернул КАР в нуль посреди ствола, аварии нет | контрольный случай |

Последствия (отпадание реле ТП, выбег привода, остановка энкодеров, действия
машиниста) следуют цепочке защиты ТП из программы ПЛК проекта. Имитатор ПЛК
не исполняет — он публикует то, что увидел бы на входах.

```bash
make run                                    # в одном терминале
make scenario                               # все сценарии по кругу
make scenario KINDS=estop_circuit_glitch ONCE=true SEED=5
make scenario-mode MODE=drive_fault         # воспроизвести запись режима
make scenario-status
make scenario-journal                       # эталон: причина, моменты, ответ
make scenario-stop
```

| Метод | Эндпоинт | Назначение |
|-------|----------|------------|
| GET | `/api/scenarios` | сценарии, режимы записей, допущения исправного состояния, статус |
| POST | `/api/scenarios/start` | `{kinds?, mode?, seed?, once?}`; пересечение наборов — 409 `signals_busy` |
| POST | `/api/scenarios/pause` | `{run_id?}` — пауза прогона, владение сохраняется |
| POST | `/api/scenarios/resume` | `{run_id?}` — продолжить; интервалы остаются точными |
| POST | `/api/scenarios/stop` | `{run_id?}` — остановить; значения остаются как были, владение освобождается |
| GET | `/api/scenarios/status` | фаза (`normal`/`episode`/`stopped`), счётчики записи, отставание |
| GET | `/api/scenarios/journal?limit=N` | журнал правды, новые первыми |

Важно:

- **Журнал правды — только для оценки.** В OPC UA он не публикуется. Не
  подавайте его станции: ответ станции сверяется с ним, а не строится из него.
- Пока идёт сценарий, ручная запись сигналов и загрузка состояний отвечают
  `409`: иначе журнал перестал бы описывать то, что видит станция.
- В режиме `real` сценарии недоступны: запись ушла бы во внешний сервер, то
  есть в настоящий ПЛК.
- Исправное состояние выведено из программы ПЛК, но полярность части входов
  однозначно из неё не следует. Список — в `GET /api/scenarios`, поле
  `assumptions`; эти значения нужно подтвердить на объекте.
- Чтобы станция увидела шаг 100 мс, в её подключении интервалы выборки и
  публикации должны быть 100 мс (по умолчанию там 1000 мс).
- Один `SEED` — одна и та же последовательность изменений.

## Режимы из реальных записей телеметрии

Помимо синтеза, имитатор воспроизводит **реальные записи** операционных
режимов подъёмной машины, импортированные из `krotkikhmaxim/temp`
(файлы `*.xlsx` — выгрузка тегов ПЛК). Режимы видны в `GET /api/scenarios`
(поле `modes`) и запускаются через `POST /api/scenarios/start {"mode": <id>}`
или `make scenario-mode MODE=<id>`:

| id | Название | Авария | Длительность |
|----|----------|--------|--------------|
| `in_motion` | В движении | нет | 120 с |
| `charged_stopped` | Заряжен (машина стоит на месте) | нет | 9 с |
| `machine_off` | Машина отключена | нет | 600 с |
| `drive_fault` | Авария привода | да | 5,4 с |
| `estop_pressed` | Нажата аварийная кнопка | да | 9,5 с |

Режим проигрывается в **темпе записи** с `SourceTimestamp` момента записи:
сначала публикуется кадр `t=0`, затем — только смены значений, как у OPC UA
подписки. Журнал правды фиксирует запуск режима (`kind`/`cause_at`/`stopped_at`
и человекописный `expected_answer`).

**Какие сигналы публикует режим.** В записях маппятся на опубликованный набор
только те сигналы, что даны напрямую и проверены: слова состояния привода и
рекуператора, скорость/ток/момент двигателя, коды ошибок, реле ТП канала 1
(`K1`/`K2`) и дискретные входы канала 2 (20A3: `SQ1/SQ3/SQ5/SQ6`, `U10–U12`,
`K2`). Слова-агрегаты `StatusDword_<module>` намеренно **не** декодируются в
отдельные теги: раскладка их битов не совпадает с биндингами имитатора
(проверено по признаку «КАР в нуле» на режиме «машина отключена»), а
непроверенный бит заставил бы станцию искать аварию, которой в объекте нет.
Остальные опубликованные теги (ШВП, ПУ, кнопки) записи не трогают и остаются
на своих значениях.

Данные режимов компактно лежат в `backend/app/services/scenario/recordings/`
(формат: JSON-заголовок + шкала смен, сжатый gzip). Переимпорт — скриптом
`scripts/import_recorded_modes.py --src <каталог с xlsx>`; при тех же входных
файлах он даёт тот же манифест (в данных хранятся `sha256` и время первой
метки каждой записи).

## Пульт машины

Вкладка «Управление машиной» — рабочий экран стенда, три шага сверху вниз:

1. **В каком состоянии запустить машину** — «Отключена», «Заряжена, стоит»,
   «В движении». Кадр состояния берётся из реальной записи телеметрии
   (`backend/app/services/scenario/recordings/<mode>.gz`, кадр t=0): слово
   состояния инвертора, скорость, ток/момент, реле ТП и дискретные входы
   канала 2. Остальные опубликованные сигналы — из `BASELINE` модели, иначе
   состояние описывало бы 20 тегов из 101.
2. **Что должно произойти** — одно воздействие: «Остановить штатно»,
   «Нажать аварийную кнопку», «Кратковременно разорвать цепь стопа»,
   «Отключить ПЧ аварийно», «Вызвать аварию инвертора», «Отключить реле ТП».
   Цепочки те же, что у эпизодов сценариев (`hoist._safety_stop`,
   `_decelerate`, `_acknowledge_and_reset`): причина → отпадание реле ТП /
   снятие привода → выбег → действия машиниста. У активного воздействия
   видно действие устранения («Отпустить аварийную кнопку», «Взвести реле
   ТП» и т. д.); одновременно активно только одно.
3. **Что происходит сейчас** — строка состояния выводится из ФАКТИЧЕСКИХ
   значений сигналов (скорость, реле ТП, цепь аварийного останова, ошибка
   привода), а не из факта нажатия, плюс последнее действие и история.

Правила жизненного цикла: выбранное другое состояние применяется только
явным новым запуском («Запустить» / «Начать заново»), «Начать заново»
очищает воздействия и историю, «Завершить тест» оставляет последние значения
для просмотра и запрещает новые воздействия. На время теста heartbeat
отключается шлюзом, а сигналы уходят под владение `machine:<session>` —
сценарий и плейбэк в это время не запускаются.

| Метод | Эндпоинт | Назначение |
|-------|----------|------------|
| GET | `/api/machine` | состояние, доступные воздействия, показания, история |
| POST | `/api/machine/start` | `{state}` — запустить в выбранном состоянии |
| POST | `/api/machine/event` | `{kind}` — применить воздействие |
| POST | `/api/machine/remedy` | устранить активное воздействие |
| POST | `/api/machine/finish` | завершить тест, значения оставить |
| POST | `/api/machine/restart` | `{state?}` — начать заново, очистить историю |

Вкладка «Записи телеметрии» — простой проигрыватель записей (выбор записи,
описание, воспроизвести/пауза/с начала, шкала времени); кнопок внесения
аварий там нет. Вкладка «Все сигналы» — прежняя таблица 101 сигнала и пульт
сохранённых состояний.

### Мнемосхема (экран вне навигации)

Старый экран «Мнемосхема» — рабочее место оператора стенда: живые значения
без обновления страницы, пульт аварий, управление плейбэком, журнал правды и
эхо станции на одном экране. Код сохранён:

- **Панель сигналов** (`MnemoPanel`) — те же 101 вход, что в таблице,
  сгруппированные по шкафам; бейджи ВКЛ/ОТКЛ, крупные значения счётчиков и
  слов PROFIBUS. Тумблеры дискретных входов работают только при свободном
  реестре драйверов: во время сценария или плейбэка они заблокированы —
  чужая запись испортила бы журнал правды.
- **Пульт аварий** (`EmergencyButtons`) — кнопки шести эпизодов сценариев
  (`estop_console`, `estop_circuit_glitch`, `drive_emergency_off`,
  `inverter_fault`, `tp_relay_dropout`, `normal_stop`) и «Стоп». Активный
  эпизод подсвечивается по статусу движка.
- **Живые значения** — WS-фид дельт (`signals_update`) с интервалом
  `VALUES_FEED_INTERVAL_S`; при обрыве — фолбэк на опрос раз в 5 с. Смена
  активного драйвера приходит как `driver_changed`.

## Плейбэк XLSX-трендов

> **Заморозка таймлайна** (ТЗ #5, §2): по умолчанию плейбэк **не пишет** в
> рабочее состояние сигналов — `play`/`seek` отклоняются с 409 «заморожен»,
> UI помечает таймлайн «отключён от управления сервером». Код и данные
> сохранены; заморозка снимается отдельным решением владельца флагом
> `PLAYBACK_WRITES_ENABLED=true` (перезапуск).

Проигрывание реальной записи с объекта: файл владельца (~260 МБ, шаг 100 мс,
~29 часов) открывается в режиме потокового чтения, память не расходуется на
объём. Колонки сопоставляются опубликованным сигналам по двум последним
сегментам пути (`Chanel1.Application.GVL.DriveGVL.ProfibusData.MotorSpeed` →
`profibus-motor-speed`); колонки вне биндингов и неоднозначные честно
попадают в отчёт `unmatched`/`ambiguous`, не угадываются.

Запись уходит в OPC UA с `SourceTimestamp` момента тренда — станция видит
шкалу объекта, а не стенда. Пишутся только смены значений, как у подписки.

```bash
make playback XLSX=/secure/path/trend.xlsx   # большой файл — по пути на сервере
make playback-control ACTION=play            # pause | resume | stop
make playback-control ACTION=play RATE=4     # скорость 0.25–8×
make playback-control ACTION=play SEEK_MS=600000  # скраб (значения на цели — текущим временем)
make playback-control ACTION=stop
```

| Метод | Эндпоинт | Назначение |
|-------|----------|------------|
| GET | `/api/playback/status` | фаза, позиция, длительность, записи, отставание |
| POST | `/api/playback/load_path` | `{path}` — открыть тренд с диска сервера |
| POST | `/api/playback/load` | multipart — прямой файл (до `PLAYBACK_UPLOAD_MAX_BYTES`) |
| POST | `/api/playback/control` | `{action, rate?, seek_ms?}` |
| POST | `/api/playback/unload` | закрыть источник |

Плейбэк — драйвер значений наравне со сценариями: взаимное исключение через
реестр (409 с именем чужого драйвера), во время проигрывания ручная запись
закрыта. Пауза держит шину; финал и «стоп» отпускают. После seek значения на
целевой позиции пишутся текущим wall-временем (немонотонные метки не
публикуются), дальше шкала снова от тренда.

## Станция: полный контур и сверка

Станция asutpv1_bigllm — наблюдатель стенда: она собирает значения по OPC UA
(`opc.tcp://<стенд>:4840`; в развёртывании — по сети `asutp-telemetry`, UI
станции — https://asutpai.ru), снимает снапшоты и рассчитывает состояние
программы. Имитатор даёт ей read-only прокси (`/api/station/*`): станция
слушает loopback без CORS намеренно, браузер стенда спрашивает её через
сервер-сайд проход. Запись в станцию закрыта белым списком маршрутов, а не
флагом; недоступность станции — `502 station_unreachable`, никогда не
притворный пустой ответ.

**Панель «эхо»** (`StationEchoPanel`) показывает, что станция видит прямо
сейчас: 101 сигнал с её собственными состояниями
(`active/inactive/connection_missing/error/bad_quality/unbound`), фильтр по
состояниям, обновление 2 с. Если сигнал серый «нет связи» — сначала связь, а
не вердикт.

**Сверка с журналом правды** закрывает контур: сценарий создаёт эпизод с
причиной; кнопка «Снапшот и сверка» в журнале правды снимает снапшот станции
(live_batch), просит её рассчитать состояние и сравнивает:

- `cause_check` — каждая причина эпизода против значения в снапшоте
  (`match/mismatch/not_bound/absent`; причина, невидимая после остановки —
  `estop_circuit_glitch` — сверке не подлежит: `history_only`);
- `state_check` — ожидаемое состояние всех сигналов на момент остановки
  (журнал записей имитатора поверх базиса исправной модели); присутствие
  точки отдельно от значения;
- `outputs` — покрытие расчёта станции (сколько выходов рассчитано, разбивка
  причин) — только наблюдение: охват станции — её свойство, а не ошибка
  стенда. Итог `pass/partial/fail` покрытие не трогает.

```bash
make station-check            # станция доступна за прокси?
make loop SEED=7              # полный контур: эпизод → снапшот → расчёт → сверка
make loop SEED=11 KIND=inverter_fault
```

`make loop` возвращает 0 только при `verdict: pass`; отчёты сверки лежат в
`scenario_runs/verifications/`. Сверить можно и уже снятый снапшот —
`POST /api/verification/report {"entry": …, "snapshot_id": …}`.

| Метод | Эндпоинт | Назначение |
|-------|----------|------------|
| GET | `/api/station/health` | прокси: жива ли станция |
| GET | `/api/station/bindings` | таблица сигналов станции с состояниями |
| POST | `/api/station/snapshots` | снимок (mode по умолчанию `live_batch`) |
| POST | `/api/station/snapshots/{id}/calculate` | расчёт состояния программой |
| GET | `/api/station/schematic/*` | листы Э3 (статус, страницы, растры) |
| POST | `/api/verification/report` | сверка: снапшот + расчёт + отчёт |
| GET | `/api/verification/list` | сохранённые отчёты, новые первыми |

## Режим heartbeat (циклическое обновление SourceTimestamp)

Переключаемый режим **heartbeat / cyclic refresh**: при включении фоновая
задача раз в секунду повторно публикует актуальные значения всех сигналов во
встроенный OPC UA сервер, даже если `Value` не изменился, присваивая им текущий
`SourceTimestamp` (UTC) и `StatusCode = Good`. Режим имитирует циклический опрос
источника и нужен для проверки клиентов, которым важна свежесть данных по
timestamp. По умолчанию heartbeat **выключен**.

Управление — через API или кнопку-тумблер `Heartbeat: OFF/ON` в шапке UI:

| Метод | Эндпоинт | Назначение | Вход | Выход |
|-------|----------|------------|------|-------|
| GET | `/api/heartbeat` | Текущее состояние режима | — | `{enabled, supported}` |
| PUT | `/api/heartbeat` | Включить/выключить режим | `{"enabled": true}` | `{enabled, supported}` |

`supported: false` (или `409` при PUT) означает, что приложение запущено не в
режиме встроенного сервера (`OPC_UA_MODE != server`) — heartbeat нечего
обновлять.

### Heartbeat и сценарии

Heartbeat и драйверы значений (сценарий, плейбэк) договариваются сами: пока
активен драйвер, шлюз глушит heartbeat — иначе он перезаписывал бы
`SourceTimestamp` и ломал шкалу события, по которой станция отличает «когда
случилось». После остановки драйвера heartbeat возвращается. Ручная запись
heartbeat не глушит: у неё нет своей шкалы.

### Семантика OPC UA

- `SourceTimestamp` в этом режиме означает время последнего циклического
  подтверждения/обновления значения, а не обязательно момент изменения
  физической величины.
- Значение и OPC UA тип при перезаписи сохраняются; меняется только
  `SourceTimestamp` (монотонно растёт) и статус фиксируется как `Good`.
- В выключенном режиме timestamp обновляется только при фактическом поступлении
  нового значения через API.
- Клиентам, которым нужны уведомления о смене timestamp без смены value,
  может понадобиться фильтр `DataChangeTrigger = StatusValueTimestamp` на
  мониторинге значений.

В будущем планируется настраиваемый интервал (`interval_ms`) и watchdog: если
данные давно не поступали во входной API, вместо бесконечного обновления
свежести возвращать `Bad_NoCommunication` / `Uncertain_LastUsableValue`.
